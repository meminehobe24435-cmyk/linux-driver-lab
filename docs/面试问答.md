## 1. 为什么用 `misc_register` 而不是自己 `setmajor` / `register_chrdev`？

三种注册方式的区别：

| 方式 | 主设备号 | 次设备号 | 设备节点 | 适用场景 |
| --- | --- | --- | --- | --- |
| `register_chrdev()` | 可以动态分配 | **固定占用 256 个** | **不创建**，要自己 `mknod` 或等 udev 规则 | 已废弃的旧接口，`Documentation/admin-guide` 里明确不建议新代码使用 |
| `alloc_chrdev_region()` + `cdev_init()` + `cdev_add()` | 动态分配 | 按需分配任意区间 | 要自己配合 `class_create`/`device_create` 才出现节点 | 需要多个次设备号、或需要独立设备类的"正经"驱动 |
| `misc_register()` | **固定 10** | 从动态池里分配一个（`MISC_DYNAMIC_MINOR`） | **自动创建** `/dev/<name>` | 只需要一个设备节点、不需要独立主设备号的杂项设备 |

本项目选 `misc_register()` 的理由：

1. **只需要一个字符设备节点**，用不上独立主设备号。内核已经为"杂项设备"准备了
   主设备号 10，把几百个驱动塞进去也不会浪费主设备号资源。
2. **设备节点和 sysfs 都由框架创建**。`misc_register()` 内部走
   `device_create_with_groups()`，于是 `/dev/labdev` 和
   `/sys/class/misc/labdev/` 自动出现；`misc_deregister()` 自动清理。
   自己用 `cdev_add` 的话要额外写 `class_create`/`device_create`/`device_destroy`，
   多出的每一步都是一个新的"忘记回滚"的机会。
3. **支持声明式 sysfs 属性**。`struct miscdevice` 有 `groups` 字段，
   `mdev.groups = labdev_groups;`（见 `labdev_main.c`）一行就把
   `buffer_size`/`debug`/`stats` 三个属性交给框架托管 —— 注册失败时框架自己回滚，
   比手工 `sysfs_create_group()` + 出错时 `sysfs_remove_group()` 少一整类 bug。
4. 代码量小，能把注意力放在真正想展示的东西（并发、ABI、生命周期）上。

**什么时候不该用 misc？** 需要多个次设备号（例如一张卡上有 4 个串口）、
需要独立设备类做 udev 规则、或者需要跟总线/设备模型做父子关系时，
就应该走 `alloc_chrdev_region` + `cdev` + `class_create`/`device_create`
（也就是 `platform_driver` 那一套）。

> 补充：`misc_register()` 会把 `struct miscdevice *` 存进 `this_device` 的
> `drvdata`，所以驱动里可以用 `container_of(dev_get_drvdata(dev), struct lab_dev, mdev)`
> 从 `struct device *` 反推出自己的设备结构体（见 `labdev_from_device()`）。

## 2. `mutex` 和 `spinlock` 怎么选？

一句话判据：**临界区里会不会睡眠？会，就只能用 mutex。**

| 维度 | `spinlock` | `mutex` |
| --- | --- | --- |
| 拿不到锁时 | 原地自旋，**一直占着 CPU** | 睡眠让出 CPU，被唤醒后重试 |
| 能否睡眠 | **绝对不能**（`copy_to_user`、`kmalloc(GFP_KERNEL)`、`msleep`、再拿一把 mutex 都不行） | 可以 |
| 能否在中断上下文用 | 可以（配 `spin_lock_irqsave` 关中断） | **不可以**，中断上下文不能睡眠 |
| 能否在 softirq/tasklet 用 | 可以 | 只能 `mutex_trylock()`，不能阻塞获取 |
| 能否递归获取 | 不能（会自死锁） | 不能（同一个 task 再拿会死锁，除非 `mutex_trylock`） |
| 持有者信息 | 无 | 有 owner，可做死锁检测（lockdep）与优先级继承（RT patch） |
| 开销 | 极低（`CONFIG_SMP=n` 且未开抢占/调试时可能被编译成内存屏障） | 一次上下文切换量级 |
| 适合的临界区 | 几条寄存器读写、链表指针操作（通常 < 几百纳秒） | 可能涉及内存分配、用户拷贝的较长临界区 |

本项目的选择及理由：

* **缓冲区 + 统计字段用 `struct mutex`**（`labdev_main.c` 的 `dev->lock`）。
  原因是持锁期间要做这些**可能睡眠**的事：
  * `copy_to_user()` / `copy_from_user()` —— 用户页可能不在内存里，会触发缺页并睡眠；
  * `kvmalloc(GFP_KERNEL)` —— 扩容时申请内存，可能睡眠等待回收；
  * `kmalloc(GFP_KERNEL)` —— 读路径上的临时缓冲。
  换成 spinlock 这些全是 bug（在原子上下文里睡眠会触发
  `BUG: scheduling while atomic`）。
* **等待队列 `wait_queue_head_t` 自带一把 `spinlock`**（`wq.lock`），
  但那是内核框架内部用的，而且只在"挂队列/唤醒"这种极短动作里持有，不牵涉睡眠。
  驱动只需要调 `wait_event_interruptible()` / `wake_up_interruptible()`。
* 本项目**没有**任何中断处理程序（`request_irq` 一次都没有），所有并发都来自
  进程上下文，所以完全不需要 `_irqsave` 变体。

如果将来要把这个设备接到真实硬件、在中断处理程序里往缓冲区塞数据，正确做法是：
缓冲区改由 `spin_lock_irqsave(&dev->slock, flags)` 保护的"中断侧队列"，
中断处理程序只做入队 + `wake_up`；而阻塞读、用户拷贝这些睡眠操作仍然在进程上下文、
用另一把 `mutex` 保护"进程侧"的数据。这就是内核里很常见的
**上半部/下半部（top half / bottom half）分离**模式。

## 3. `poll` 与 `epoll` 是什么关系？设备驱动要做什么？

**关系：epoll 完全建立在 `poll()` 之上，驱动侧不需要为 epoll 写任何额外代码。**

调用链：

```
应用: epoll_ctl(epfd, ADD, fd, {EPOLLIN})
        └─ 内核: ep_insert()
             └─ vfs_poll(file, &epq.pt)          ← 调用驱动的 .poll
                  └─ 驱动: labdev_poll()
                       ├─ poll_wait(filp, &dev->wq, wait)
                       │     └─ wait->qproc = ep_ptable_queue_proc
                       │          └─ 把 ep_poll_callback 挂到 dev->wq 上
                       └─ 返回当前的 EPOLLIN/EPOLLOUT 位掩码

数据到达: 驱动 write() 里 wake_up_interruptible(&dev->wq)
        └─ 内核: ep_poll_callback()  →  把该 epitem 挂进 epfd 的就绪链表
             └─ 应用: epoll_wait() 立刻返回
```

所以驱动只需要做两件事：

1. **在 `poll()` 里先 `poll_wait()` 注册，再检查状态，最后返回掩码。**
   顺序不能反！如果先检查状态、发现没数据就直接返回，那么"检查完到挂队列"之间
   到达的数据就会被漏掉 —— 这就是经典的**丢唤醒（lost wakeup）**。
   `poll_wait()` 自身不会睡眠，它只做登记。
2. **在状态真正发生变化的地方调用 `wake_up`。** 本项目在 `labdev_write` 成功写入后、
   `ioctl RESET` 后、扩容后都调用了 `wake_up_interruptible(&dev->wq)`。
   少调一处，`epoll_wait` 就可能永远不返回。

`labdev_poll()` 的具体返回值：

```c
poll_wait(filp, &dev->wq, wait);

mutex_lock(&dev->lock);
dev->poll_count++;
if (ringbuf_avail(&dev->rb) > 0)
        mask |= EPOLLIN | EPOLLRDNORM;
mask |= EPOLLOUT | EPOLLWRNORM;   /* 写永不阻塞(满了就覆盖)，所以永远可写 */
mutex_unlock(&dev->lock);

return mask;
```

**水平触发（LT，默认）和边沿触发（ET，`EPOLLET`）的区别与驱动的关系：**

| | 水平触发（默认） | 边沿触发（`EPOLLET`） |
| --- | --- | --- |
| 语义 | 只要条件成立就**一直**上报 | 只在**状态发生变化**的那一刻上报一次 |
| 内核行为 | 每次 `epoll_wait` 都重新调一次 `file->f_op->poll` 复查 | 只有在就绪链表里有条目时才返回，返回时把条目摘掉，之后不再复查 |
| 应用的责任 | 可以在任意时刻只读一部分 | **必须一次读到 `EAGAIN`**，否则剩下没读的数据再也不会触发事件 |
| 驱动的责任 | 只要 `poll()` 返回正确掩码就行 | 同上，但**每一次状态变化都必须 `wake_up`**，否则应用永远卡住 |

驱动侧的代码在两种模式下**完全一样**，区别全在用户态怎么写。
这就是为什么本项目 `dtest.c` 里专门测了水平触发的行为
（有数据 → `EPOLLIN`；读空 → 不再上报；注册 `EPOLLOUT` → 立即返回）。

**为什么 `poll` 也要处理 `poll_table` 为 NULL 的情况？**
`select()`/`poll()` 与 `epoll` 共用同一套 `struct poll_table_struct`。
`poll_wait()` 内部对 `p->qproc == NULL` 有保护，所以驱动不用自己判空 ——
但要知道 `poll()` 可能被"不带等待队列"地调用（例如 `epoll` 重新轮询
就绪状态的调用路径），所以 `poll()` 里**不能假设自己一定会被挂到队列上**。

## 4. `kthread` 怎么安全退出？为什么不能在拿锁之后 `kthread_stop()`？

### 正确姿势

```c
static int labdev_kthread_fn(void *data)
{
        struct lab_dev *dev = data;

        while (!kthread_should_stop()) {          /* ① 每轮都检查 */
                mutex_lock(&dev->lock);
                dev->heartbeat++;
                mutex_unlock(&dev->lock);

                /* ② 用可被唤醒打断的睡眠 */
                msleep_interruptible(heartbeat_ms ? heartbeat_ms : 1);
        }
        return 0;                                  /* ③ 靠 return 退出，不要 do_exit() */
}
```

```c
static void __exit labdev_exit(void)
{
        /* ④ 必须在碰 dev->lock 之前停线程 */
        if (dev->kthread) {
                kthread_stop(dev->kthread);        /* 阻塞到线程真正返回 */
                dev->kthread = NULL;
        }
        misc_deregister(&dev->mdev);
        kvfree(dev->mem);
        kfree(dev);
}
```

四条规则：

1. **循环条件必须用 `kthread_should_stop()`。** `kthread_stop()` 会先设置
   `KTHREAD_SHOULD_STOP` 标记，再 `wake_up_process()`，最后用 completion
   等线程退出。线程看到标记就该退出循环。
2. **睡眠必须是"可被打断的"。** `kthread_stop()` 靠 `wake_up_process()` 唤醒线程。
   如果线程睡在一个 `kthread_stop()` 唤不醒的地方（例如等一个永远不会有人
   `complete()` 的 completion、或者 `wait_event()` 在一个没人会 `wake_up` 的队列上），
   `kthread_stop()` 就会**永久阻塞**，`rmmod` 卡死。
   本项目的 `msleep_interruptible()` 底层是 `schedule_timeout()`，
   `wake_up_process()` 能立刻把它唤醒，所以 `rmmod` 不用等满一个心跳周期。
3. **退出要用 `return`，不要 `do_exit()`。** 线程函数正常返回后 kthread 框架会
   做清理并完成 completion，`kthread_stop()` 才等得到。
4. **顺序：先停线程，再碰共享数据和锁。** 这是最容易踩死锁的地方：

```
┌─ rmmod 线程 ─────────────┐        ┌─ kthread ──────────────┐
│ mutex_lock(&dev->lock)   │        │ mutex_lock(&dev->lock) │ ← 在等 rmmod 放锁
│ kthread_stop(k)  ← 等 k 退出      │                        │
└──────────────────────────┘        └────────────────────────┘
                两边互等 → 死锁
```

   如果反过来写成 `mutex_lock()` 再 `kthread_stop()`，就会出现上图的死锁。
   本项目 `labdev_exit()` 里第一件事就是 `kthread_stop()`，之后才动 `dev->lock`
   和 `dev` 的内存。

**额外要点：**

* `kthread_stop()` 之后**才能** `kfree(dev)`，否则线程可能在用已经释放的内存。
* 不要在 `kthread_stop()` 之后再去取 `kthread_should_stop()` 之外的状态 ——
  线程已经停了，`dev` 也要释放了。
* 线程名用 `kthread_run(fn, data, "labdev-hb")` 里的 `"labdev-hb"` 指定，
  在 `ps`/`dmesg` 里能直接认出来。
* 如果只是想偶尔做点事、不需要一个常驻线程，用 **delayed work**
  （`INIT_DELAYED_WORK` + `schedule_delayed_work` + `cancel_delayed_work_sync`）
  更省资源 —— 它跑在系统的 workqueue 上，不占一个独立 task_struct。
  本项目选 `kthread` 是为了把"内核线程的创建/调度/退出"这件事显式地展示出来。

## 5. `copy_from_user` / `copy_to_user` 为什么是必需的？

直接用 `memcpy(buf, user_ptr, n)` 是**错的**，而且是能拿到 root 的那种错。原因有五层：

### （1）用户指针根本不可信：可能指向内核空间

用户态可以传任意数值当指针。如果没有检查，`write(fd, (void *)0xffff888000000000, 8)`
就变成了"**从用户态改写内核内存**"—— 教科书级的本地提权漏洞。
`access_ok()` + `copy_*_user()` 里的地址范围检查会拦住它
（这就是为什么本项目在 `read`/`write` 入口先做一次 `access_ok()`）。

### （2）用户页可能不在内存里，访问会缺页

用户缓冲区可能被换出到 swap、可能是 `mmap` 的文件页、可能还没分配物理页。
直接访问会触发**缺页异常**。在内核里缺页是允许的，但前提是内核知道
"这次访问是用户访问，失败要优雅处理"：

* `copy_to_user()` 底层用 `__copy_to_user`/`rep movs`，配套的异常表项
  （`extable`）会让缺页异常把控制流跳到"拷贝失败"的出口，返回**未拷贝的字节数**；
* 换成 `memcpy`，同一个缺页就会变成内核 oops ——
  因为内核缺页处理程序会认为这是内核 bug。

**返回值语义**：`copy_to_user()` 返回**没拷贝成功的字节数**，所以
`if (copy_to_user(...)) return -EFAULT;` 才是正确的写法。

### （3）SMAP / PAN：硬件层面禁止内核碰用户页

x86 的 **SMAP**（Supervisor Mode Access Prevention）和 ARM 的 **PAN**
会在 CPU 层面让内核态访问用户页直接触发 #PF。
`copy_*_user` 内部会正确地用 `stac`/`clac` 指令临时打开这个允许位
（见 `arch/x86/lib/copy_user_64.S`）。手写 `memcpy` 在开了 SMAP 的机器上
会直接崩。

### （4）有些架构用户和内核地址空间不是同一套

在不使用 KPTI 的历史架构上，用户地址空间和内核地址空间可以是不同的页表；
`copy_*_user` 里有架构相关的实现来切换页表或做必要的处理。

### （5）附带的安全语义

* `copy_from_user` 在拷贝不满时会把目标缓冲区**剩余部分清零**，
  避免把内核栈/堆上的旧数据泄漏给调用者；
* 结合 `objtool`/`checker` 还能做一些静态审计。

### 本项目的具体用法

```c
/* 读：先 access_ok 粗查，再 access_ok + copy_to_user */
if (!access_ok(ubuf, count))
        return -EFAULT;
...
if (copy_to_user(ubuf, kbuf, got)) {
        /* 失败必须回滚读游标，否则数据在用户态“凭空消失” */
        ringbuf_seek(&dev->rb, -(long)got, RB_SEEK_CUR);
        kfree(kbuf);
        mutex_unlock(&dev->lock);
        return -EFAULT;
}
```

这里有个容易忽略的点：**"先消费数据、再往用户态拷"是错的**。
用户随便传一个坏指针，就能把设备缓冲区里的数据吃掉（一种信息丢弃/DoS）。
正确做法要么像本项目这样**拷贝失败时回滚游标**，
要么先 `peek` 确认能拷贝成功再真正消费。

> **`access_ok()` 和 `copy_*_user()` 的关系**：`access_ok()` 只是一次
> **廉价的地址范围合法性检查**（不访问内存、不处理缺页），用来尽早拒绝
> 明显非法的指针；真正保证安全的是 `copy_*_user()` 自己的异常处理。
> 内核 5.0 之后 `access_ok()` 的 `type` 参数被去掉了，
> 只剩 `access_ok(ptr, size)`。

## 6. `wait_event_interruptible` 为什么不会丢唤醒？

本项目的阻塞读长这样（`labdev_read()`）：

```c
for (;;) {
        avail = ringbuf_avail(&dev->rb);
        if (avail > 0)
                break;

        if (filp->f_flags & O_NONBLOCK) {
                mutex_unlock(&dev->lock);
                return -EAGAIN;
        }

        dev->wait_count++;
        mutex_unlock(&dev->lock);                       /* ① 先放开锁 */
        ret = wait_event_interruptible(dev->wq,
                                       dev->rb.used != dev->rb.consumed);  /* ② 再睡 */
        if (ret)
                return -ERESTARTSYS;
        mutex_lock_interruptible(&dev->lock);           /* ③ 醒来重新加锁 */
}
```

关键是 `wait_event_interruptible()` 展开后的顺序：

```c
prepare_to_wait_event(&wq, &wait, TASK_INTERRUPTIBLE);  /* 先把本进程挂进等待队列 */
if (condition)                                          /* 挂完队列之后才复查条件 */
        break;
schedule();                                             /* 真的睡了 */
```

也就是 **"先入队，再复查条件"**。设想的竞态是：

```
CPU0 (读者)                         CPU1 (写者)
unlock(mutex)
                                   lock(mutex); 写入数据; unlock(mutex)
                                   wake_up_interruptible(&wq)   ← 此刻队列上没人
prepare_to_wait_event(...)  ← 入队
if (condition)              ← 条件为真！break，根本不睡
```

因为入队发生在复查条件**之前**，即使唤醒"提前"发生，读者也会在
`if (condition)` 那里发现条件已成立而直接返回，绝不会睡死。
这就是"不会丢唤醒"的正式理由 —— 需要 **入队与条件检查之间不存在窗口**，
而 `prepare_to_wait_event` 之后立刻检查条件正是为了消除这个窗口。

**反例（会丢唤醒的写法）：**

```c
/* 错误！ */
if (ringbuf_avail(&dev->rb) == 0)
        wait_event_interruptible(dev->wq, ringbuf_avail(&dev->rb) > 0);
```

这里的 `if` 判断和 `wait_event` 内部的入队之间存在窗口，写者可能正好
卡在中间完成全部动作并唤醒 —— 而队列上还没人，唤醒丢失。
**必须把条件检查放进 `for(;;)` 循环里、由 `wait_event` 自己复查。**

**为什么醒来后要重新加锁、重新检查？** 因为被唤醒不等于条件成立
（可能被 `ioctl RESET`、被扩容、被另一个读者抢走数据，或者只是被信号打断）。
标准写法就是"等待必须包在循环里"。

> 由于 `wait_event_interruptible` 内部会重新加锁前的那次检查是**不加锁地读**
> `dev->rb.used != dev->rb.consumed`，这是刻意的、良性的数据竞争：
> 它只是个提示，真正的判据在重新拿到 `mutex` 之后的 `ringbuf_avail()`。
> 能说清楚"为什么这里不加锁是安全的"，比机械地到处加锁更能体现理解。

## 7. 阻塞读为什么必须"先解锁再睡"？

如果持着 `dev->lock` 去睡：

```
读者: lock(mutex) → sleep（等数据）          ← 锁一直被读者占着
写者: lock(mutex) → 永远拿不到锁 → 永远写不进数据
结果: 数据永远不来，读者永远不醒 —— 死锁
```

所以 `labdev_read()` 进入等待前一定 `mutex_unlock(&dev->lock)`，
醒来后重新 `mutex_lock_interruptible()` 并回到循环开头重新判断。

**这就是 `mutex` 与 `wait_event` 组合的标准形态**，也是"临界区里不能睡眠"
这条规则的一个具体体现：睡眠会让出 CPU，如果此时还占着锁，
其他需要这把锁的任务全部卡住。

> 顺带说明另一个选择：内核也提供
> `wait_event_interruptible_locked_irq()` 这类"持锁等待"的变体，
> 但它们要求等待队列头**共用同一把锁**（`wait_queue_head_t` 内部自带
> `spinlock`），而本项目用的是 `mutex`，两者不是同一把锁，
> 所以只能用"解锁—睡—重新加锁"的模式。

## 8. `ioctl` 命令为什么要用 `_IOR/_IOW/_IOWR` 宏编码？

`_IOC()` 把一个 32 位整数拆成四段：

```
 31 30 29 ... 16 15 ... 8 7 ... 0
┌────┬──────────┬────────┬───────┐
│dir │  size    │  type  │  nr   │
│2bit│  14bit   │  8bit  │ 8bit  │
└────┴──────────┴────────┴───────┘
 方向  参数大小    magic    序号
```

| 段 | 位宽 | 含义 |
| --- | --- | --- |
| `dir` | 2 | `_IOC_NONE`/`_IOC_WRITE`/`_IOC_READ`，即数据方向 |
| `size` | 14 | 参数结构体的字节数（`sizeof(...)` 由宏自动算出来） |
| `type` | 8 | magic 字符，用来区分不同驱动（本项目是 `'L'`） |
| `nr` | 8 | 命令序号 |

好处：

1. **参数大小被编进命令里。** 用户态头文件和内核模块不是同一个版本时，
   `sizeof` 不同，命令整数值就不同，内核 `switch` 匹配不上 → 返回 `-ENOTTY`，
   **而不是用错误的长度去读写用户内存**（那会直接破坏用户态内存）。
   本项目 `dtest.c` 专门测了这个：
   ```c
   /* magic/序号都对，但参数大小是 lab_config(16B) 而命令定义是 lab_stats(64B) */
   ioctl(fd, _IOR(LAB_IOC_MAGIC, 4, struct lab_config), &cfg);   /* → -ENOTTY */
   ```
2. **magic 把设备区分开。** 避免 A 驱动的命令被误送到 B 驱动上执行。
3. **方向信息让内核能提前检查。** `_IOC_DIR(cmd) & _IOC_READ` 时用
   `access_ok(uarg, _IOC_SIZE(cmd))` 做范围检查（照
   `Documentation/driver-api/ioctl.rst` 的推荐写法）。
4. **`_IOWR` 可以双向。** 本项目 `LAB_IOC_SET_CONFIG` 用 `_IOWR`：
   用户传进期望配置，内核**回填实际生效的配置**，用户态一眼就能看出
   哪些值被接受了、哪些被夹取或忽略了（例如 `buffer_size=0` 表示"别改"）。
   这比"设置成功但不知道设成什么"友好得多。

**ABI 稳定性**：结构体只用定宽类型（`__u32`/`__u64`），并在
`lab_ioctl.h` 里用编译期断言钉死大小：

```c
LAB_STATIC_ASSERT(sizeof(struct lab_config) == 16, "lab_config ABI 大小必须为 16 字节");
LAB_STATIC_ASSERT(sizeof(struct lab_stats) == 64, "lab_stats ABI 大小必须为 64 字节");
```

内核和用户态都包含这个头文件，任何一侧改了结构体布局，**编译期**就会炸，
不会等到运行时才出问题。另外结构体里留了 `reserved` 字段并要求必须为 0，
为将来加字段留好了位置（不改变大小、不破坏 ABI）。

## 9. `unlocked_ioctl` 和老的 `ioctl` 有什么区别？

| | `ioctl`（老的） | `unlocked_ioctl`（现在用的） |
| --- | --- | --- |
| 引入时间 | 很早期 | 2.6.11 起 |
| 调用时是否持有 **BKL**（大内核锁） | **是** | **否** |
| 并发性 | 全局串行化 | 由驱动自己用 mutex/spinlock 保证并发安全 |
| 入参 | `(inode, file, cmd, arg)` | `(file, cmd, arg)` |
| 现状 | 基本只剩历史兼容 | `struct file_operations` 里的标准字段 |

历史背景：早期内核整个是个大锁（BKL），所有 `ioctl` 串行执行，性能极差。
`unlocked_ioctl` 就是"**不持 BKL 的 ioctl**"的意思，把并发保护的
责任下放给驱动自己。

所以用 `unlocked_ioctl` 的代价是：**驱动必须自己保证并发安全**。
本项目的做法是所有 ioctl 都走 `dev->lock`（mutex），
并且改动状态前先把参数校验做完（`labdev_ioc_set_config()` 里在拿锁之前
就把 `flags`/`reserved`/`buffer_size` 全部检查一遍，非法就直接返回，
不留下"改了一半"的状态）。

> 还有 `compat_ioctl`：32 位程序在 64 位内核上跑时，`struct` 布局和指针宽度可能不同，
> 需要提供 `compat_ioctl` 做转换。本项目的结构体只用 `__u32`/`__u64`
> 且都是定宽标量、没有指针，32/64 位布局一致，所以不提供也是安全的 ——
> 但这属于"因为设计得好所以不需要"，不是"可以不管"。

## 10. `try_module_get(THIS_MODULE)` 在 `open()` 里做什么？

它给模块引用计数 **+1**，`release()` 里 `module_put()` **-1**。

作用：**防止"还有 fd 指向模块代码时就把它卸载掉"。**

没有它会发生什么：

```
1. 进程 A: fd = open("/dev/labdev")      ← 拿到了 labdev_fops
2. root:  rmmod labdev                   ← 模块内存被释放
3. 进程 A: read(fd, ...)                 ← 跳进已释放的代码 → 内核崩溃
```

有它之后，`rmmod` 时模块引用计数不为 0，`delete_module()` 返回 `-EBUSY`，
用户看到：

```
rmmod: ERROR: Module labdev is in use
```

这是**正确**的行为。所以 `open()` 里：

```c
if (!try_module_get(THIS_MODULE))
        return -ENODEV;          /* 模块正在被卸载 */
```

`release()` 里：

```c
module_put(THIS_MODULE);
```

**注意两个坑：**

1. **必须在所有失败路径上都 `module_put()`。** 如果 `open()` 在
   `try_module_get()` 之后还有可能失败的分支，那条分支也要放引用，
   否则引用计数泄漏，模块**永远卸不掉**。
   本项目把 `try_module_get()` 放在 `open()` 的最前面，
   之后只有不可能失败的语句 + 一次加锁自增，就是为了让这条路径简单到不会出错。
2. **测试程序必须真的关掉所有 fd**，否则 CI 里 `rmmod` 会报 `EBUSY`。
   本项目 `stress.py` 里所有 fd 都用 `try/finally: os.close(fd)` 保证释放，
   子进程用 `p.join()` 等干净；CI 最后一步还会专门检查
   `/proc/modules` 里是否真的没有 `labdev`。

另外，`kthread` 也是"模块代码正在被使用"的一种形式，但它不靠引用计数保护 ——
`module_exit` 里的 `kthread_stop()` 保证线程在任何内存被释放之前已经退出。

## 11. `llseek` 在字符设备上应该怎么实现？

先问一个问题：**这个设备是"字节流"还是"可随机访问的对象"？**

* **真正的流设备**（管道、终端、鼠标）语义上不可 seek。
  标准做法是在 `open()` 里调 `nonseekable_open(inode, filp)`，
  它清掉 `FMODE_LSEEK`，VFS 之后就会用 `no_llseek` ——
  应用调 `lseek()` 得到 `-ESPIPE`。
* **可随机访问的设备**（framebuffer、块设备、内存映射式设备）才实现真正的 seek。

本项目介于两者之间：它是 FIFO 字节流，但**缓冲区里的数据在被覆盖之前一直保留**，
所以"回退重读"是有意义的。于是实现对读游标的相对定位（见 `labdev_llseek()`）：

| `whence` | 基准 |
| --- | --- |
| `SEEK_SET` | 缓冲区里最老的那个字节 |
| `SEEK_CUR` | 当前读游标（允许负偏移，用于回退） |
| `SEEK_END` | 缓冲区末尾（已缓冲数据之后） |

越界或 `whence` 非法返回 `-EINVAL`。

**必须知道的坑：不要在 `open()` 里随便调 `nonseekable_open()` 或 `stream_open()`。**
它们会清掉 `FMODE_LSEEK`，而 `vfs_llseek()` 是这么写的：

```c
loff_t vfs_llseek(struct file *file, loff_t offset, int whence)
{
        loff_t (*fn)(struct file *, loff_t, int);

        fn = no_llseek;
        if (file->f_mode & FMODE_LSEEK) {      /* ← 标志没了就走 no_llseek */
                if (file->f_op->llseek)
                        fn = file->f_op->llseek;
        }
        return fn(file, offset, whence);
}
```

`FMODE_LSEEK` 是 `do_dentry_open()` 默认设置的，但 `nonseekable_open()` /
`stream_open()` 会清掉它。清了之后**你写的 `llseek` 永远不会被调用**，
`lseek()` 一律返回 `-ESPIPE` —— 一个非常隐蔽的 bug（代码看着没错，
调试起来毫无头绪）。本项目 `labdev_open()` 里特意留了注释说明这一点。

**语义一致性**：既然"数据读到之后还留在缓冲区里可以回退"，
那就不能出现"刚好读空就把游标归零"这种特例 ——
否则会出现"写 100、读 50、回退能重读 100 字节"但
"写 100、读 100、回退什么都没有"的诡异不一致。
本项目为此专门去掉了 `ringbuf_read()` 里的"读空即归位"逻辑
（这个 bug 是被 `tests/ringbuf_test.c` 的随机模糊测试抓出来的：
参考模型和实现在"读空"这一点的处理不同，模糊测试立刻报出了状态分歧）。
现在规则只有一条：**回退能力消失的唯一时刻，是数据被新写入覆盖的时候。**

## 12. 为什么用 `kvmalloc` 而不是 `kmalloc`？

`kmalloc()` 要求**物理连续**的内存。请求 1 MiB 就是 256 个连续页（order-8），
系统运行一段时间后内存碎片化，这种高阶分配**很容易失败**
（即使总空闲内存还很充裕）。

`kvmalloc(size, gfp)` 的行为是：

1. 先试 `kmalloc(size, gfp | __GFP_NORETRY)` —— 成功就拿到快速、物理连续的内存；
2. 失败就退回 `vmalloc(size)` —— 用不连续的物理页拼出**虚拟地址连续**的空间。

对本项目来说，环形缓冲区只需要"**虚拟地址连续**"（因为要 `memcpy` 和按下标访问），
不需要物理连续（不做 DMA），所以 `kvmalloc` 是正解：
小尺寸时和 `kmalloc` 一样快，大尺寸时不会因为碎片而失败。

配套的三条纪律：

* 分配用 `kvmalloc()` / `kvzalloc()`，释放**必须**用 `kvfree()`，
  不能混用 `kfree()`（用 `kfree` 释放 `vmalloc` 来的内存是内存破坏）；
* `kvmalloc` 可能在 `GFP_KERNEL` 下睡眠，所以**不能在自旋锁/原子上下文里用**；
* 如果这块内存要给 DMA 用，就必须坚持 `kmalloc`/`dma_alloc_coherent`
  并要求物理连续 —— `kvmalloc` 不合适。

本项目缓冲区上限设成 1 MiB（`LAB_MAX_BUF`）也是为了不让单次
`write()` 的内存拷贝代价失控。

## 13. `DEVICE_ATTR_RW` 的 `_store` 里为什么不能直接 `kstrtobool` 之后就完事？

```c
static ssize_t debug_store(struct device *d, struct device_attribute *attr,
                           const char *buf, size_t count)
{
        struct lab_dev *dev = labdev_from_device(d);
        unsigned int val;
        int ret;

        ret = kstrtouint(buf, 0, &val);     /* ① 解析失败要原样返回错误码 */
        if (ret)
                return ret;
        if (val > 1)                        /* ② 只接受 0/1，写 2 要 -EINVAL */
                return -EINVAL;

        mutex_lock(&dev->lock);             /* ③ 和驱动其他路径共用同一把锁 */
        dev->debug = !!val;
        mutex_unlock(&dev->lock);

        return count;                       /* ④ 成功必须返回 count，不能返回 0 */
}
```

四个容易忘的点：

1. **返回 `count`，不是 0。** sysfs 的 `store` 约定：成功时必须返回
   **被消费的字节数**（也就是入参 `count`）。返回 0 会被上层当成"什么都没写"，
   用户态的 `write()` 会看到 0，`echo 1 > ...` 也可能报错。
2. **用 `kstrtouint`/`kstrtobool` 而不是 `simple_strtoul`**（后者已过时，
   不报错、不检查溢出），并且**把解析错误码原样返回**（`-EINVAL`）。
3. **要真的拒绝非法值。** 只用 `kstrtobool` 的话 `0`/`1`/`y`/`n` 都能过，
   但如果你想要"只接受 0 和 1"，就得自己加 `if (val > 1) return -EINVAL;`。
   本项目的 CI 专门测了这个：`echo 2 > .../debug` 必须失败。
   （这条也常被用来测试**驱动有没有做参数校验**，是很好的面试细节。）
4. **和驱动其他路径共用同一把锁。** `debug` 虽然只是开关日志，但它被
   `labdev_dbg()` 宏在 `read`/`write`/`ioctl` 路径里读，所以要么加锁，
   要么用 `WRITE_ONCE`/`READ_ONCE` 明确表达"这是无锁的标量读写"。
   本项目选了加锁，简单且不容易错。

另外：`_show` 里用 `sysfs_emit(buf, ...)`（5.10+）而不是 `sprintf()` ——
因为 `sysfs_emit` 会自己限制不越过 `PAGE_SIZE-1`，并在越界时给警告。
本项目对老内核做了版本判断自动退回 `scnprintf(buf, PAGE_SIZE, ...)`：
```c
#if LINUX_VERSION_CODE < KERNEL_VERSION(5, 10, 0)
#define sysfs_emit(buf, fmt, ...) scnprintf((buf), PAGE_SIZE, fmt, ##__VA_ARGS__)
#endif
```

## 14. 模块卸载时怎么保证没有内存泄漏和残留设备节点？

把"申请"和"释放"排成**严格相反**的两列，任何一步失败都跳到对应的回滚标签：

```c
static int __init labdev_init(void)
{
        dev = kzalloc(sizeof(*dev), GFP_KERNEL);          /* ① */
        if (!dev) return -ENOMEM;

        dev->mem = kvmalloc(buf_size, GFP_KERNEL);        /* ② */
        if (!dev->mem) { kfree(dev); return -ENOMEM; }    /*    回滚 ① */

        ret = misc_register(&dev->mdev);                  /* ③ */
        if (ret) goto err_free_mem;                       /*    回滚 ②① */

        dev->kthread = kthread_run(...);                  /* ④ */
        if (IS_ERR(dev->kthread)) goto err_deregister;    /*    回滚 ③②① */

        return 0;

err_deregister:
        misc_deregister(&dev->mdev);
err_free_mem:
        kvfree(dev->mem);
        kfree(dev);
        return ret;
}
```

```c
static void __exit labdev_exit(void)
{
        labdev_stop_kthread(dev);      /* 必须先于碰锁，见 Q4 */
        misc_deregister(&dev->mdev);   /* /dev/labdev 与 sysfs 属性一起消失 */
        kvfree(dev->mem);
        kfree(dev);
        labdev_dev = NULL;
}
```

要点：

* **回滚顺序与申请顺序相反**，用 `goto` 标签串联（内核里这是标准写法，
  比层层嵌套 `if` 清晰得多）。
* **`misc_deregister()` 会连带清理设备节点和 sysfs 属性**。
  如果把 sysfs 属性用 `miscdevice.groups` 交给框架托管（本项目的做法），
  就不存在"忘记 `sysfs_remove_group`"的问题。若手工创建，
  则必须 `sysfs_remove_group()` **先于** `misc_deregister()`。
* **`kthread_stop()` 必须在 `kfree(dev)` 之前**，否则线程可能访问已释放内存。
* **错误路径也要按顺序回滚，不能只 `return -ENOMEM` 了事** ——
  否则第一次失败时 `kzalloc` 的内存就泄漏了。
  这也是为什么本项目的 CI 会检查 `dmesg`（看有没有
  `kmemleak` 之类的告警）以及卸载后 `/dev/labdev`、`/sys/class/misc/labdev`
  三处是否都真的消失。

**验证手段**：

* `rmmod` 后检查 `/proc/modules`、`/dev/labdev`、`/sys/class/misc/labdev`
  三处都消失（CI 里就是这三条 `test`）；
* 打开 `CONFIG_DEBUG_KMEMLEAK` 跑一遍；
* `SLUB_DEBUG` 的 `slub_debug=FZPU` 内核参数可以在释放后填充特殊值，
  释放后使用会立刻暴露；
* `KASAN` 是最强的工具，但要在 `CONFIG_KASAN=y` 的内核上跑；
* 加载/卸载循环几百次，看 `dmesg` 和 `/proc/meminfo` 的 `Slab` 是否单调增长。

## 15. 中断上下文为什么不能睡眠？

"睡眠"的本质是：把当前任务的状态置为 `TASK_INTERRUPTIBLE`/`TASK_UNINTERRUPTIBLE`，
调用 `schedule()` 主动让出 CPU，等条件满足后再被唤醒。

中断上下文里做不到这件事，原因是：

1. **中断上下文没有"当前任务"可以挂起。** 硬中断处理程序运行在
   **被中断的那个任务的栈**上（借用它的内核栈），它不是一个独立的
   `task_struct`。如果你在这里 `schedule()`，被中断的任务就被"顺带"挂起了，
   而它根本不知道自己被挂起，也就没有任何人会去唤醒它 —— 系统直接卡死。
    softirq 更是可能运行在 `ksoftirqd` 或中断返回路径上，情况类似。
2. **它占着 CPU 资源且不能被抢占。** 中断处理程序运行期间（至少在
   `irqentry` 到 `irqexit` 之间）本 CPU 上的中断是被屏蔽或部分屏蔽的，
   此时睡眠会导致该 CPU 上的其他中断也被延迟，实时性崩溃。
3. **持有自旋锁时睡眠会造成死锁。** 想象 CPU0 在持锁状态下睡去，
   而抢锁的 CPU1 一直在自旋等锁 —— CPU1 就永远在那里烧 CPU，
   而锁的持有者永远醒不过来。

因此内核用 `might_sleep()` / `in_atomic()` 主动检查，
一旦在原子上下文里调用了可能睡眠的函数，就会打印
`BUG: sleeping function called from invalid context`。

**哪些操作会睡眠？**

| 会睡眠 | 不会睡眠 |
| --- | --- |
| `kmalloc(GFP_KERNEL)` | `kmalloc(GFP_ATOMIC)` |
| `copy_to_user()` / `copy_from_user()` | `memcpy()` |
| `mutex_lock()` | `spin_lock()` |
| `msleep()` / `ssleep()` / `schedule_timeout()` | `udelay()` / `ndelay()` |
| `wait_event*()`（不带 `_atomic` 的） | `spin_trylock()` |

**本项目的体现**：因为完全没有中断处理程序，所有并发都来自进程上下文，
所以可以放心用 `mutex` + 会睡眠的 `copy_*_user`。
但如果要把这个驱动改成"真实硬件 + 中断"的版本，就必须：

* 中断处理程序里只做 `spin_lock_irqsave()` 保护的最小动作（入环形缓冲区 + `wake_up`），
  绝不做 `copy_to_user`、绝不 `kmalloc(GFP_KERNEL)`、绝不拿 `mutex`；
* 把耗时的处理放到 **tasklet / workqueue / 线程化中断（`request_threaded_irq`）**里去做；
* 内核里 `request_threaded_irq()` 提供的"上半部 + 内核线程下半部"机制，
  正是为了能在"中断响应"和"可以睡眠的复杂处理"之间划清界限。

## 附：本项目一句话速查

| 问题 | 一句话答案 |
| --- | --- |
| 为什么 misc？ | 单设备节点场景最省代码，节点/sysfs 由框架自动创建和回滚 |
| mutex 还是 spinlock？ | 临界区里要 `copy_*_user`/`kvmalloc`（会睡）→ 必须 mutex |
| poll 和 epoll？ | epoll 建立在 `poll()` 上，驱动只需"先 `poll_wait` 再查状态"+ 状态变化处 `wake_up` |
| kthread 怎么退？ | `while(!kthread_should_stop())` + 可唤醒的睡眠；`kthread_stop()` **必须在拿锁之前** |
| 为什么 `copy_*_user`？ | 用户指针不可信（可能是内核地址）、可能缺页、SMAP 禁止内核直访用户页 |
| 为什么不丢唤醒？ | `wait_event` 是"先入队、再复查条件"，入队与检查之间没有窗口 |
| 为什么 `_IOR` 宏？ | 把大小编进命令，用户态/内核头文件不一致时返回 `-ENOTTY` 而不是写坏内存 |
| 为什么 `try_module_get`？ | 防止还有 fd 时卸载模块导致跳进已释放代码 |
| 为什么 `kvmalloc`？ | 1 MiB 需要高阶连续页，`kmalloc` 在碎片下会失败，`vmalloc` 兜底 |
